# 跨设备追剧记录软件 —— 设计方案 v1（已确认定稿）

> 依据：桌面需求文档《跨设备追剧记录软件 —— 给 DeepSeek Harness 的需求说明》
> 用户回答：后端 PocketBase｜个人单用户｜TMDB 内置国内镜像+可自备 Key｜观看平台=国内平台+暂无固定平台｜MVP 端=Android + Web

## 1. MVP 范围

**做（P0）**
- 手动记录闭环：TMDB 搜索补全（内置国内镜像，可配置自备 API Key；无 Key 时降级纯手动）→ 添加剧 → 选季/集 → 记录进度（第几分钟）、观看设备、观看时间、备注 → 标记某集看完 / 整剧看完 → 补录历史记录
- 数据来源标记与保护：每条进度带 `来源=手动/自动`；手动改过带"已手动修改"标识，自动记录不得静默覆盖
- 账号与同步：PocketBase 单管理员，Android + Web 登录同一账号，实时同步；离线先记录、联网自动补传
- 自动记录：截图 OCR 生成"建议记录"→ 审核（确认/合并/忽略）；自动去重；冲突提示
- 部署：Docker Compose 一键（PocketBase + 前端静态托管 + 可选 OCR 容器）；README + 部署说明 + MIT
- 交付端：Android APK + Web（PWA，适配电视浏览器大屏与遥控操作）

**不做（后续版本）**
- Jellyfin/Plex/Emby webhook 插件（仅框架预留接口）
- Android 通知监听解析（P1）、CSV 导入（P1）、Trakt（P2）
- iOS（需 macOS 打包）、Android TV 原生端、多用户账号

## 2. 同步方案对比：自托管同步 vs WebDAV / 本地文件同步

| 维度 | 自托管 PocketBase（推荐） | WebDAV（坚果云等） | 本地文件同步（Syncthing 类） |
|---|---|---|---|
| 实时性 | 秒级实时推送（SSE） | 手动/轮询 | 两端在线时实时 |
| 多端冲突 | 服务端统一处理，乐观并发 + 变更流水 | 无锁，易互相覆盖 | 生成冲突副本，需人工合并 |
| 离线支持 | 客户端本地队列，联网自动补传 | 天然文件缓存 | 天然，但需两端同时在线 |
| 部署成本 | 一台常开设备（NAS/云/家里电脑） | 零 | 两端都装客户端 |
| 数据隐私 | 完全私有 | 存第三方网盘 | 点对点 |
| MVP 工作量 | 低（PB 自带账号/实时/存储） | 中（自写文件合并逻辑） | 中（引入同步客户端依赖） |

**结论**：主架构 = 自托管同步；WebDAV 不进 MVP，仅做「JSON 导出/导入」作为备份与迁移兜底。

## 3. 数据模型（PocketBase collections）

```
shows 剧
  id, name, original_name, tmdb_id(unique,可空), first_air_date,
  poster_url, overview, total_seasons, source: tmdb|manual, created, updated

progress 进度（每剧每集一条，去重核心）
  id, user→users, show→shows, season_number, episode_number,
  position_seconds 看到第几分钟, duration_seconds 本集时长(可空),
  device: mobile|tv|web|other, watched_at 观看时间,
  episode_completed bool, show_completed bool,
  note, source: manual|auto, manually_edited bool,
  created, updated
  唯一约束: (show, season_number, episode_number)  ← 同一集不会重复记录

pending_records 自动建议记录（待审核）
  id, show→shows(可空,未匹配时),
  source_plugin 插件名, raw_payload json 原始数据(OCR文本/截图路径),
  parsed json 解析结果, match_season, match_episode, match_position_seconds,
  confidence 0-1, dedup_key unique 去重键,
  status: pending|confirmed|merged|ignored, created

history_log 变更流水（补录追溯/冲突排查, append-only）
  id, progress→progress, field, old_value, new_value, source, created_at
```

**冲突规则**（服务端 hook 实现）：自动确认动作仅允许作用在 `status=pending` 的建议上；若目标 progress 的 `manually_edited=true`，只能「合并并保留手动修改」或「忽略」，不能覆盖。去重：`(show, season, episode)` 唯一约束 + 建议记录 `dedup_key` 唯一约束。

## 4. 自动记录来源优先级

按用户现状（国内平台、无固定媒体库）调整：

| 优先级 | 来源 | MVP 状态 | 说明 |
|---|---|---|---|
| P0 | 截图 OCR | ✅ 实现 | 手机/网页上传播放截图 → OCR 识别剧名/集数/进度 → 生成建议记录 → 人工确认。全平台通用 |
| P0 | 手动记录 | ✅ 实现 | 永远保底的路径 |
| P1 | Android 通知解析 | 预留 | 监听视频 App 播放通知（"剧名 第X集"），适配工作量大 |
| P1 | Jellyfin/Plex/Emby webhook | 插件框架预留 | 将来自建媒体库即插即用 |
| P1 | CSV 导入 | 预留 | 历史记录迁移兜底 |
| P2 | Trakt | 不做 | 需外网，价值低 |

> ⚠️ 原验收标准写的是"至少接入 Jellyfin/Plex/Emby 之一"，但用户目前不用媒体库。建议 MVP 自动记录来源改为**截图 OCR**，验收标准同步改为"能上传截图 → 生成建议记录 → 审核确认"。待用户确认。

OCR 实现方案：后端挂可选 PaddleOCR 容器（CPU 可跑，镜像约 5GB，中文识别好，数据不出服务器）。识别结果本来就是"建议"、需人工确认，偶尔认错不影响数据正确性。不想加容器也可先纯手动，OCR 留作插件。

## 5. 开发步骤

| 阶段 | 内容 | 产出 |
|---|---|---|
| 0 | GitHub 仓库 + MIT + monorepo 结构（apps/web、infra、docs） | 可提交的仓库骨架 |
| 1 | PocketBase schema 迁移 + 服务端 hooks（去重/冲突/保护）+ Docker Compose（pb + 前端静态 + 可选 paddleocr）+ 初始化脚本 | 后端一键可跑 |
| 2 | Web 前端：React + Vite + TS，登录、TMDB 搜索（镜像+Key 配置）、剧库/进度页、手动记录表单 | 手动闭环可演示 |
| 3 | 离线队列：本地缓存 + 待同步队列 + 冲突提示 | 断网可记录 |
| 4 | 截图 OCR → 建议记录 → 审核界面（确认/合并/忽略） | 自动记录闭环 |
| 5 | Capacitor Android 打包 APK（含截图分享入口）+ Web PWA 电视适配 | 两端交付 |
| 6 | README/部署文档 + 按 MVP 验收标准自测 + 发布 GitHub | 可开源交付 |

## 已确认（4 点，2026-10-25）

1. 自动记录 MVP 来源改为**截图 OCR**（验收标准同步调整，见需求文档）。
2. OCR 采用**自托管 PaddleOCR 容器**（约 5GB 镜像，作为可选服务，未部署时 App 仍可纯手动使用）。
3. 先本地开发；Docker 按通用设计交付（兼容 NAS/云服务器）。
4. 软件命名 **「剧迹 DramaTrace」**（仓库名 dramatrace）。
